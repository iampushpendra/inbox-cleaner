## What does the complete content inventory show, and what needs fixing first?

### Takeaway
The problem is product/content drift before it is publishing volume: 41 of 47 article bodies describe the Gmail API, 33 instruct readers to click Connect Gmail, while current extension source uses DOM automation and Gmail's own selection/Trash controls. Fix those journeys and evidence before expanding the queue; inventory decisions are hypotheses for review, not proven search cannibalization.

## How should publishing, measurement and the next 90 days work on very little cash?

### Takeaway
Use a versioned evidence pipeline, not a calendar quota. Start with repairs and a small number of complete assets; increase output only when accuracy, distinct utility and measured activation stay intact.

### Cited Findings
- Google says featured snippets are selected by its systems, not publisher markup, and official guidance prioritizes useful, accurate, original work and transparent authorship. [Featured snippets](https://developers.google.com/search/docs/appearance/featured-snippets); [helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content).

### Inferences
Publishing gates, implemented as automated checks plus evidence review:

1. **Intent gate:** one target job and primary owner URL; compare existing inventory/queued topics; one-sentence original contribution. Similarity detection flags a review, never auto-deletes content.
2. **Product truth gate:** versioned machine-readable product facts imported into drafts: installed release, supported device/locale, no OAuth for extension, scan scope/limits, exact-versus-approx counts, sender-wide archived/starred reach, Trash not permanent delete, no unsubscribe/size scan/scheduling unless implemented. Reject contradictory body, metadata, schema and CTA instructions.
3. **Instruction evidence gate:** official sources for Gmail/provider/tax/security claims; safe test account procedure and screenshot for UI-dependent steps; source date, tested version/device, expected result and recovery. Claims about performance, reliability, time or storage savings need measured results, otherwise remove or qualify. No “always,” “no timeouts,” or invented example outcomes.
4. **Editorial gate:** named real author, last verified date, answer scope, preserve important mail, device limits and conflict-of-interest disclosure in comparisons. Use whatever length answers the job. FAQs only if useful; no mandatory five or question-only H2 rule. Keep Article metadata accurate; drop HowTo/FAQ rich-result promises.
5. **Build gate:** correct canonical/status, parseable HTML/JSON, one H1, meaningful unique title/description, valid internal/official links, mobile layout, accessible screenshots, install CTA correct, schema agrees with visible claims. Dates cannot be future; `dateModified` changes only for substantive updates. Local image counts and content facts should be reportable per release.
6. **Release gate:** article starts draft, becomes evidence-checked, then publish-ready; generator builds only publish-ready entries. Preview diff and repair failures before commit. Keep existing clean-tree/remote-verification controls. Audit scheduled job separately before resuming automatic publication; no unilateral workflow changes were made here.

**Cadence:** initial 2–3 evidence-complete content/asset releases per week as a capacity budget, plus unlimited small factual repairs, rather than 4 new articles/day. This is not an SEO optimum. Increase as many as pass the gates with a genuinely different useful outcome; measure backlog drift, defect rates and support cost as well as visits.

**Measurement with minimal cash:** use Search Console and Chrome Web Store developer reporting already available to the owner; optional free website analytics only after privacy review. Export weekly GSC page/query/device/country impressions, clicks, CTR, index status and canonical. Separate branded/nonbranded queries. Track website organic landing visits → store outbound clicks by article/placement → store listing/install totals → user success using aggregate, privacy-consistent methods. A store click is not an install, and listing installs do not automatically reveal the source article. Preserve unknown attribution instead of presenting a fabricated funnel. Website event payloads must exclude Gmail addresses, sender domains, query strings containing personal data, email content and message IDs. Do not silently add extension telemetry that contradicts local-only privacy promises; prefer voluntary anonymous success/feedback or local-only counters until explicitly designed.
