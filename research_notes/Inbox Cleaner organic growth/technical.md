# Technical SEO and conversion audit — Inbox Cleaner

Audit date: 2026-10-17 (Asia/Kolkata). Read-only inspection of repository and live HTTP, plus official Google documentation. No production changes. Findings below distinguish source HTML from browser-rendered behavior; browser rendering, Rich Results Test, Search Console and field performance data were not available to this audit. A first web text extraction briefly showed 46 guides, but direct HTTP/site crawl afterward confirmed the current 47-guide site and local/live identical homepage bytes; use the latter as current evidence.

## Can search engines discover and consolidate the intended pages?

### Takeaway
The static site already has a working crawl foundation: 50 current sitemap URLs all returned HTTP 200, descriptive unique titles/descriptions, static content, and internal links. The immediate technical work is cleanup and consolidation rather than buying a new SEO platform or replacing the framework.

All 50 listed URLs returned 200 in a concurrent HTTP crawl. ### Inferences
- **Priority 1:** keep one canonical host and migrate GitHub Pages traffic page-for-page to it where hosting permits. If server redirects are unavailable on Pages, use a deliberate static migration/redirect setup with canonical fallback and usable destination links, then update store/other owned links. Do not simply block the duplicate in robots before Google can process canonical signals. Buying a custom domain is optional; a stable free hostname can support the initial growth work.
- **Priority 1:** move `docs/superpowers/` and store submission instructions outside the public output or exclude them via an explicit public-site build allowlist. Serving internal planning prose is not a useful landing experience. For intentionally public non-HTML documents requiring exclusion, use `X-Robots-Tag: noindex`; robots Disallow alone does not reliably remove a known URL.
- **Priority 2:** normalize index.html aliases with 301/308 redirects and add privacy self-canonical. At 50 pages these are hygiene, not evidence of a catastrophic crawl-budget problem.
- **Priority 2:** retain the working static generator and add topic hubs with curated relationships rather than replacing existing discovery. The token-based related algorithm often starts with chronological neighbors; editorial topic links would improve user relevance even though current posts are not orphaned.

### Gaps
- No Search Console Page Indexing/URL Inspection access: submitted sitemap, actual indexed count, chosen canonical, queries, impressions, manual actions, and crawl history are unknown. A site: query would not settle those questions.
- No complete external backlink inventory or hosting dashboard access: cannot quantify duplicate-host authority or verify the best platform-level redirect option.
- HTTP-to-HTTPS request returned 308 (urllib reported it as an exception); a full redirect chain was not independently measured, so do not claim chain quality.

## Are page presentation and structured data helping users and search?

### Takeaway
Main content is server-delivered HTML and can be read without client-side app execution. The strongest presentation opportunity is to add firsthand product evidence and useful topic navigation; spending time on FAQ/HowTo rich-result optimization is misplaced because those Google features are deprecated.

### Cited Findings
- **Confirmed, raw HTML/live text extraction:** homepage and articles expose main headings and copy in original HTML. Home has a descriptive title, description, canonical, and one H1. Article example has Article + HowTo + FAQPage JSON-LD in its source. — [home head/H1](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:8), [article metadata and schema](/Users/pushpendrasingh/projects/inbox-cleaner/docs/blog/how-to-bulk-delete-gmail-emails.html:7), [live example](https://inbox-cleaner.vercel.app/blog/how-to-bulk-delete-gmail-emails.html).
- **Confirmed, local source inventory:** 47 of 47 article HTML files include `Article`; 44 contain `FAQPage` and 44 contain `HowTo`. No BreadcrumbList or SoftwareApplication was found in source HTML. That last finding is source-only: no rendered-DOM absence claim or validation claim is made. — [representative article schemas](/Users/pushpendrasingh/projects/inbox-cleaner/docs/blog/how-to-bulk-delete-gmail-emails.html:13), [home schema](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:15).
- **Confirmed, official current docs:** FAQ rich results stopped appearing May 7, 2026; Google removed feature documentation June 15, 2026. Older advice saying FAQ is available to authoritative health/government sites is superseded. HowTo rich results were deprecated September 2023. — [Google Search documentation updates, May/June 2026](https://developers.google.com/search/updates), [Google HowTo deprecation announcement](https://developers.google.com/search/blog/2023/08/howto-faq-changes).
- **Confirmed, live HTTP:** homepage advertises `/og-image.png`, which returns 404. Local public directory has no corresponding file. ### Inferences
- **Priority 1 quick win:** create a real share image or remove the nonexistent OG reference until one exists. Add product and Gmail workflow screenshots with accurate captions, alt text, and safe redacted/demo inbox data.
- **Priority 2:** preserve useful visible FAQs, but stop measuring success in FAQ/HowTo rich-result eligibility. Keep accurate Article entity/date information; consider breadcrumbs and verified application/organization identity only where they describe visible facts. Never invent reviews or aggregate ratings.
- **Priority 2:** curate entry hubs such as sender cleanup, storage cleanup, Gmail search operators, and safe deletion. At this size a topic filter or grouped hub is enough; elaborate pagination/search infrastructure is premature.
- **Priority 2:** measure mobile Lighthouse/PageSpeed Insights and real CrUX/GSC field data before optimizing speed. Separating marketing homepage from legacy Gmail app would allow loading OAuth code only when needed, but its benefit must be measured.

### Gaps
- No rendered mobile/desktop inspection or screenshot evidence: layout, tap targets, actual overflow, keyboard experience, and dynamically injected schema remain untested.
- No Rich Results Test: presence is proven, eligibility and validity are not.
- No Lighthouse, CrUX, PageSpeed field metrics or GSC CWV report: no Core Web Vitals pass/fail statement is justified.

## Does the organic landing/install funnel build justified trust?

### Takeaway
The primary conversion risk is inconsistent product truth across the landing page, old articles, privacy policy, and store listing. Fix this before mass publication: the site simultaneously promotes extension and OAuth browser workflows, while some claims contradict Gmail itself and the actual extension implementation.

### Cited Findings
- **Confirmed:** homepage says Gmail selects a maximum 50 per page and estimates 20+ clicks for 1,000 emails, although its own FAQ correctly mentions Gmail's all-conversations link. Google's Gmail help explicitly shows selecting all 2,000 conversations via that link. — [comparison copy lines 153–177](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:153), [home FAQ lines 38–40](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:38), [official Gmail help](https://support.google.com/mail/answer/9259770?hl=en).
- **Confirmed:** a high-intent bulk-delete guide repeats a hard 50-email limitation in title-description context, introduction and quick answer; its schema says Inbox Cleaner uses Gmail API with no practical limit. The current extension instead operates Gmail's existing select-all matching link and Trash button. — [article lines 8, 45–50, 94–97](/Users/pushpendrasingh/projects/inbox-cleaner/docs/blog/how-to-bulk-delete-gmail-emails.html:45), [content.js selectAllMatchingAndTrash](/Users/pushpendrasingh/projects/inbox-cleaner/content.js:330).
- **Confirmed:** home includes primary Add to Chrome CTA plus Try browser version, inline legacy Connect Gmail tool, a pro waitlist, and Google OAuth scripts. This is two product workflows plus an additional lead-capture goal on the same landing page. — [hero actions](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:122), [embedded tool](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:263), [scripts](/Users/pushpendrasingh/projects/inbox-cleaner/docs/index.html:371), [live homepage](https://inbox-cleaner.vercel.app/).

### Inferences
- **Priority 1:** create a single product-truth inventory covering extension/browser differences, scope of inbox scanning, time bounds, permissions, deletion/recovery, categories, supported device and Workspace limits. Rewrite home, privacy, article boilerplate and store description consistently from it. Validate broad claims such as “fastest,” “every sender,” “entire inbox,” and “no practical limit,” or replace with specific verified behavior.
- **Priority 1:** teach the free native Gmail select-all flow accurately. Differentiate the extension on ranked senders, multi-sender discovery/selection and review convenience. A trustworthy answer can still convert users who need those features.
- **Priority 1:** make extension installation the clear primary path; isolate browser OAuth into an explicitly labeled separate route if retained. Do not say the browser version is broken without testing. Preserve it until product decisions and usage data support removal.
- **Priority 1:** update Chrome Web Store description and owned inbound links to match shipped version and canonical domain; publish accurate privacy explanations for each product surface.
- **Priority 2:** add privacy-conscious aggregate funnel measurement with explicit product policy decisions: organic landing → guide → store click → installed extension → first scan → first successful cleanup. Page views alone cannot establish activated acquisition. Search Console and Web Store dashboards can provide zero-cost initial baselines; do not promise full attribution between site and extension without implementation.
- **Acceptance criteria for first implementation phase:** consistent product facts and policy, OG asset HTTP 200, internal docs absent from public build, preferred-host links everywhere, sitemap and relevant links tested, native Gmail guidance accurate, measurements/baseline documented. These are finite coding tasks with minimal cash cost.

### Gaps
- Actual OAuth user flow, installation permissions shown to users, Workspace admin restrictions, first scan/deletion success, user feedback, and extension telemetry were not exercised. Do not infer usability success from source or store availability.
- Store user count is a point-in-time public figure, not active-user count, organic install count, or revenue. No conversion rate or organic baseline is known.
